# U1：schema4→5 升级、恢复与期间事件补回

状态：可先设计；实现依赖 T0，迁移入口与 F0 协调。
分支建议：`feat/update-schema-migration`。执行时从最新 main 创建独立 worktree；当前没有创建该分支。
共用约束：[索引与回报格式](README.zh-CN.md)；[契约提案](../architecture-addendum.zh-CN.md)。

## 目标

让 P1 能安全通过升级链路进入真实安装，同时明确失败恢复时的事件一致性。

## 范围与复用

- 以 internal/updater 为主，首个支持范围只做 schema4→5；迁移编号和 schema5 定义复用 F0，不新增第二套迁移。
- 定义停止写入、维护提示、SQLite 一致性备份、迁移、候选健康检查、提交成功和失败恢复；不要只复制 db 主文件忽略 WAL。
- 服务不可用期间，现有 hook spool/新增必要持久队列保留事件；只有事件已持久化才允许成功确认。恢复后按基线与事件 ID 幂等补回。
- 明确旧 hook/新 hook 和旧后端能否解码期间事件；未知新种类不能悄悄丢弃或伪装成成功，须保留待重放并可查看原因。
- 用户面板写入在维护阶段明确拒绝/重试，不返回已成功再丢写入；不自动批准过期请求，不把恢复事件当成新交付。

## 不做

不取消所有 schema 守卫；不引入生产签名/自动安装；只支持已证明的迁移组合。

## 验收标准

1. 合成 v4 数据升级后历史、用户状态和关联不丢，schema5 的信号列正确。
2. 每个替换/迁移/健康检查失败点与中途退出都可恢复整组程序和一致数据库。
3. 升级前后重复、迟到和补回事件只有一次业务效果，未支持事件仍可恢复。
4. 备份可校验恢复、预检空间与路径错误可解释；真实安装、密钥和数据未改。

## 验证

用合成 SQLite、假的程序组和故障注入做完整事务/竞态检查；测试成功后再由用户另行安排真实升级。 每条标准写满足/不满足/无法验证；模拟 expected 不得填成真实已通过。

## 交付

隔离升级记录、故障矩阵、恢复步骤及草稿 PR；正式升级仍是独立动作。 按共同六段格式回报，附精确候选、证据和未验证项；没有 PR 则明确仅设计/调研。用户确认与执行者自测分开。
