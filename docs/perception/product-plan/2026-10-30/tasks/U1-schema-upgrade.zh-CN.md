# U1：schema4→5 升级、恢复与期间事件补回

状态：可先设计；实现依赖 T0，schema 定义与 F0 协调；**本轮仅修订方案，全部机制尚未实现**。
分支建议：`feat/update-schema-migration`。执行时从最新 main 创建独立 worktree；当前没有创建该分支。
共用约束：[索引与回报格式](README.zh-CN.md)；[契约提案](../architecture-addendum.zh-CN.md)。

## 目标

让仍在 schema4 的安装有可达的 schema5 升级入口，并在失败恢复时保住已经确认的事件。

## 发布顺序与用户选择

现有旧升级器在 `Eligible`、检查/准备阶段按编译时 StoreSchema 拒绝不同 schema，尚未进入迁移就会拦住 schema5。仅在 schema5/F0 中加入新升级逻辑不能让旧安装收到它。以下两条路线须用户 U05 二选一；本 PR 没有代选或启动发布：

1. **过渡升级器路线。** 先开发、合并并发布仍使用 schema4 的 U1 过渡版，使其理解已签名、受限的 4→5 迁移描述、维护屏障和恢复事务；逐台确认所有目标设备已安装且运行该过渡版后，才允许正式发布 F0/schema5。未升级设备不得直接收到 schema5 安装提议。不能取消通用 schema 守卫。
2. **一次性手动路线。** 用户明确选择手动 schema4→5，在隔离环境证明整组备份、迁移与恢复，再另行安排各目标设备操作；不能假称旧内置升级器已支持，也不能借手动路线跳过事件/权限保护。

F0 可并行构建隔离整合候选；U1 不依赖 F0 先发布，迁移编号/schema 定义只是协调输入。正式发布的前置关系是“U1 过渡版全目标安装或获准手动路线 → F0/schema5”，合并、发布、安装分别记证据。

## 范围与复用

- 以 internal/updater 为主，首个支持范围只做 schema4→5；迁移编号和 schema5 定义复用 F0，不新增第二套迁移。旧 `Recover` 假设同 schema 且不恢复数据库，不能直接据此声称跨库回滚安全。
- 定义停止写入、维护提示、SQLite 一致性备份、迁移、只读候选健康检查、持久提交和失败恢复。冻结写入后记备份水位并核实 checkpoint/备份完整性，不只复制 db 主文件忽略 WAL。
- 本提案选择下述“提交前 hook 拒收屏障”，不依赖已向新版 ACK 的事件随后凭空出现在 v4 备份中。若实现改用导出 events.body 的补回方案，须先补充新设计与故障证明，不能静默换策略。
- 明确旧 hook/新 hook 和旧后端能否解码期间事件；未知种类在出队前持久隔离到仅本用户可读的待重放文件，记录事件 ID、原因与计数，不能悄悄丢弃或伪装成成功。
- 用户面板写入在维护阶段明确拒绝/重试，不返回成功后丢写入；不把恢复事件当新交付，不自动重放过期权限决定。

## 拟议事件屏障与提交点（尚未实现）

1. 先建立下述拒收屏障并排空在途写事务，再核实 v4 一致备份；备份水位包含屏障前所有已确认事件，屏障后不再产生待回滚的新 ACK。迁移事务持久记录原版本、候选、备份校验与阶段。
2. 直到整个升级事务**持久提交之前**，所有 `/hook/*` 返回 503，不产生成功 ACK、不允许候选写入业务事件；hook 保留现有 spool。健康检查只读，不以探测写入绕过屏障。面板写入也拒绝。维护路由应先于新旧后端切换建立，所有失败路径保持屏障。
3. 迁移与候选只读健康检查成功后，先持久提交事务，再开放 hook ACK 与写入；恢复器依据持久提交标记处理“已提交但尚未开放”窗口。提交前失败可回 v4；提交后不得再用旧备份覆盖 v5 已确认事件，后续故障属于 v5 恢复，不能伪装成可无损回旧库。
4. 提交前回滚时继续拒收，恢复旧程序和一致 v4，再按兼容版本/事件 ID 幂等重放已排队事件。旧版不能解码的种类先持久隔离到待重放区并显示缺口；验证持久保存成功才能从原队列移除。整个策略保证已确认事件不因回旧库丢失，未确认事件仍受有限队列约束。

## 维护窗口、有限队列与权限降级

- 现有 spool 默认最多 **2,000** 条，达到上限会丢弃最旧项并累加 `dropped` 计数，不是无限日志。预检记录深度/上限、可用空间、丢弃基线；余量或计数无法核实时停止升级，不把未知当 0。
- 拟议候选维护时限 **120 秒**，实现前须随故障测试复核。超过时限立即停止继续安装并尝试回滚；恢复本身失败时维持 503，显示真实不可用时间和失败原因，不能谎称总停机必然小于 120 秒。
- 维护界面显示已过时间、当前阶段、排队深度/上限、丢弃总数与本次增量、待重放/失败计数、回滚结果。检测本次 dropped 增量大于 0 时停止继续升级并明确事件缺口，不能承诺未确认事件零丢失。
- `PermissionRequest` 遇 503、超时或 SS 不可用时回到 **Claude 原生询问**，不得自动允许、静默沿用旧决定或把队列补回当作当前批准。维护结束后仍按当前请求指纹/有效期判断，过期请求由原生流程重新询问。

## 不做

不取消所有 schema 守卫；不引入生产签名/自动安装；只支持已证明的迁移组合。

## 验收标准

1. 旧 v4 升级器直接拒绝 v5 的用例先成立；所选过渡版全目标安装门槛或手动门槛可核对，不能出现发布依赖倒置。路线选择单列用户决定。
2. 合成 v4 数据升级后历史、用户状态和关联不丢，schema5 信号列正确；一致备份包括 WAL，校验与恢复可重现。
3. 对屏障建立、备份、迁移、替换、只读健康检查、持久提交前后与开放 ACK 的每个退出点注入故障；提交前回旧库不丢已确认事件，提交后不覆盖已确认 v5 数据。
4. 重复/迟到/补回只产生一次业务效果；未知种类持久待重放、2,000 条溢出丢弃计数、维护超时和恢复失败都可见且不伪报成功。
5. 维护中 PermissionRequest 回原生询问，过期/重复请求不自动批准；面板拒绝写入。空间、路径、余量未知可解释，正式安装、密钥和数据未改。

## 验证

用合成 SQLite、假的程序组和故障注入做完整事务/竞态检查；测试成功后再由用户另行安排真实升级。 每条标准写满足/不满足/无法验证；模拟 expected 不得填成真实已通过。

## 交付

隔离升级记录、故障矩阵、恢复步骤及草稿 PR；正式升级仍是独立动作。 按共同六段格式回报，附精确候选、证据和未验证项；没有 PR 则明确仅设计/调研。用户确认与执行者自测分开。
