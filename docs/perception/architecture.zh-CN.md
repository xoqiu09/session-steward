# 感知架构

状态：设计已确认（2026-10-29），按分期实现。本文只描述 SS 如何持续知道项目进展，不扩大任何现有采集范围；每扩大一次范围，先改本文并经用户同意。

## 目标

用户不手动汇报，SS 也能持续、准确地知道：

- 在 GitHub 网页上合并了 PR，小镇及时更新，并收起已经过时的合并提醒。
- Codex / Claude Code 会话在继续工作、等待输入、失败或交付时，小镇及时反映出来。
- 每个信号都挂到正确的项目、工作项、会话和 PR 上。
- 小猫用本地模型解释进展、指出状态矛盾；客观事实由程序核实，不靠模型。
- 用户验收、代码合并、实际安装、运行验证分四类分别记录，互不代替。

## 不做的事

- 不接入 Computer History：它的内置摘要会经过 OpenAI 服务器处理，和“完全本地理解”的要求冲突。以后如果要接，需要另行设计本地获取和处理的路径，并单独征得同意。
- 不读取、不保存、不上送对话正文。会话记录只取结构化字段。
- 不做屏幕录制或键盘记录，不观察 SS 获准范围以外的应用。
- 飞书个人消息收件箱先不做，等前几期稳定后另写设计。
- 模型不直接改任何状态，也不代替用户验收。

## 四条原则

1. **事实、观察、解释分三层。**
   - 事实：可以用程序再核对一次的东西，例如 Git 里目标分支是否包含某个提交、PR 是否已合并、进程是否存在。
   - 观察：采集到的信号，例如一次 hook 事件、会话记录里的一行。观察可能迟到、重复、乱序。
   - 解释：模型给出的推断，例如“这个工作看起来卡在等测试账号”。
   - 解释只能作为“提议”显示，不能改变工作项、会话、审批的状态。
2. **每个信号都带来源和时间。** 至少包含：来源类型、设备、发生时间、收到时间，以及一个能回查的引用（hook 事件 ID、会话记录位置、PR 号加提交 SHA、进程号加启动时间）。模型的判断还要记下模型名、生成时间和所依据的信号。
3. **本机采集，摘要同步。** 每台电脑上的 SS 采集自己的会话、进程和文件；中心机（Mac Studio）只接收摘要，不直接观察其他电脑。摘要沿用现在的规则：不含对话、命令、工具预览、目录路径、恢复命令和审批内容。
4. **没有信号就记为“信息缺口”，不判定为卡死。** “30 分钟没有任何来源的新信号”和“进程已经不在了”“正在等你输入”是三种不同的状态，界面上分开写。

## 数据流

```text
采集器（每台电脑本地）
  hook 适配器 ─┐
  会话记录增量读取 ─┤
  进程核对 ─┤──> 统一事件 ──> Ingest（去重、乱序保护）──> 状态机
  Git / GitHub 核对 ─┘                                        │
                                                              v
                                   快照 ──> 面板 / 小镇 / 每日十分钟
                                     │
                                     ├──> 摘要 ──> 中心机合并视图
                                     └──> 小猫（本地模型）──> 解释（提议）──> 面板单独一栏
```

现有的 `event.Event`、`Ingest` 的去重和乱序保护、WorkItem / Session / Run / Approval 的分离都保留，新采集器只是多几个往 `Ingest` 送事件的入口，以及几个定时核对器。

## 关键设计

### 1. 信号的来源和时间

- `events` 表已经有 `occurred_at` 和 `received_at`。新增来源字段：`hook`、`transcript`、`process`、`git`、`github`、`hub`、`model`、`user`，以及回查引用。
- 快照里每个工作项、每个会话都给出“最近一次信号”：来源、时间，以及距今多久。小镇和每日十分钟据此写“5 分钟前 · hook”或“2 小时没有信号”。
- 同一件事有多个来源时，用“发生时间更新的覆盖旧的”。发生时间相同，按 hook > 会话记录 > 进程推断的优先级。这和现在的乱序保护一致。

### 2. GitHub 感知

- 工作项和 PR 的关联：用 `仓库 + 分支名 + head SHA` 找 PR。只有分支名对得上还不够，head SHA 也要一致，沿用现在合并证据的规则。
- 对每个关联了 PR 的、还没完成的工作项，定时取 PR 的状态：开着、已合并、被关闭，还有检查结果（通过、失败、进行中）和合并提交。
- 网页上合并以后，以“合并提交已经包含在刚拉取的目标分支里”为准，把工作项标为已合并，并收起对应的合并提醒。“已合并”仍然只有一个来源，就是核对器。
- 只用用户自己的 `gh` 登录，写操作前核对账号；SS 自己永远只读 GitHub。频率按需要退避：有待处理的工作就 1 分钟一次，没有就不查。

### 3. 会话记录增量读取（补漏）

- 每个会话文件记下读到的位置（文件、inode、偏移量），只往后读，文件被截断或替换时从头重读。
- 只解析结构化字段：时间、事件类型、工具名、`tool_use_id`、退出码或成功失败、等待输入的标记、token 计数。对话正文、工具输入输出、文件内容一律不读进内存以外的地方，也不落库。
- 产生的事件标为 `transcript` 来源。和 hook 重复的事件按 `会话 + tool_use_id + 类型` 去重，hook 已经记过的就跳过。
- 主要用途：SS 停机、hook 失败、hook 暂存没补发时，把漏掉的“工具失败”“停止”“等待输入”补回来。

### 4. 非托管会话的存活核对

- Claude：读 `~/.claude/sessions/<pid>.json` 里的进程号和进程启动时间，再用进程列表核对这个进程是否还在、启动时间是否一致（防止进程号被复用）。
- Codex：先调研本地有没有类似的记录；没有就只按“打开了对应会话文件的进程”做弱判断，并标明是弱判断。
- 结论只有三种：进程在、进程不在、不知道。“进程不在”且最后的事件不是 `Stop` / `SessionEnd` 时，写“会话意外结束”，不写“卡死”。

### 5. 小猫的接口

- SS 提供一个只读接口，给出每个工作项的结构化事实：状态、各来源的最近信号、证据、信息缺口、验收和合并状态。不含对话正文。
- 小猫通过一个写入接口提交“解释”：工作项、种类（进展总结、发现矛盾、待核对事项、归属建议）、一两句文字、所依据的信号引用、模型名、生成时间。
- 面板单独用一栏显示“小猫的看法（模型推断）”。用户可以点“不对”或“知道了”，这两种操作都只记录用户的反馈，不改变工作项状态。
- 小猫适合发现的矛盾，例如：
  - Agent 说已交付，但最近一次验证失败；
  - 工作项显示进行中，但进程已经不在两小时了；
  - 已合并但还没验收；
  - 已验收但还没装到任何一台电脑上。

### 6. 四类完成记录

| 记录 | 谁能写 | 依据 |
| --- | --- | --- |
| 用户验收 | 只有用户 | 用户在面板点击 |
| 代码合并 | 只有核对器 | 目标分支包含提交，或经核对的 PR 合并证据 |
| 实际安装 | 只有核对器 | 某台电脑正在运行的 SS 版本，包含这个工作的合并提交 |
| 运行验证 | 核对器或用户 | 安装后的健康检查结果；需要人工确认的由用户记录 |

Agent 自述、测试通过、模型判断都不能写入这四类记录。它们只作为证据显示。

## 已决定（用户 2026-10-29 确认）

1. **小猫先只在 Mac Studio 上运行**，读中心机的合并视图。其他电脑的工作只有摘要，信息较少；不够用时再考虑每台电脑各跑一个。
2. **摘要里加“信号来源和时间”**：只加来源类型和时间，不加内容和回查引用。这样中心机也能显示“2 小时没有信号”。
3. **补装这些 Claude hooks**：`PermissionDenied`、`CwdChanged`、`PreCompact`/`PostCompact`、`TaskCompleted`，以及 Notification 的 `agent_completed`、`quota_auto_resume_*`。`PostToolBatch`、`MessageDisplay` 太频繁，不装；`WorktreeCreate`/`WorktreeRemove` 会替代 Claude 默认的 Git 行为，不装。
4. **GitHub 查询频率**：有待处理的工作时，每个仓库每分钟最多一次；没有就不查。所有项目合计每小时不超过 300 次请求。
5. **会话记录读取默认开启**，只读结构化字段，设置里可以关掉。
