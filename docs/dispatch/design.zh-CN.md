# 派活台：在 MacBook 上给 Mac Studio 派活

状态：设计稿，待独立审查；**没有实现，也没有改任何网络、密钥或安装**。
来源：用户 2026-10-31 的四项决定（见第 2 节）；本机控制原型 PR #42（[说明](../native-codex-prototype.zh-CN.md)）；[共用契约第 6 节](../perception/product-plan/2026-10-30/architecture-addendum.zh-CN.md#6-仅控制执行设备的本机控制提案)。
任务书：[K1～K4](tasks/README.zh-CN.md)。

## 1. 它是什么

小镇广场上现在有验收台、告示栏、退件架。派活台是第四张桌子：在这里给 Mac Studio 交代任务，Studio 用 Codex 执行，进度、交付和验收照旧回到小镇对应项目的房子里。

- **执行只在 Mac Studio。** MacBook 和以后的手机都只是“派活的地方”，不在本机执行，也不能指定 Studio 以外的电脑执行。
- **一件任务就是一个工作项。** 不另建任务库；派活台显示的是 Studio 上由派活台发起的那些工作项，以及它们的 Codex 会话和审批。
- **它和 PR #42 原型的关系。** 原型证明了 Codex app-server 这条路能走通（开始、停止、恢复、交付、本机审批、页面断开继续跑）。派活台把这些能力并进正式的 `steward serve`，原型的独立程序和隔离 home 不再需要。只参考原型的做法和测试，不保留两份“当前状态”。
- **Ekko 只参考（U08 已定）。** 不复制、不改写它的代码和依赖。

## 3. 两条路分开

现在两台电脑之间已经有一条“多设备只读推送”（8443，`/api/hub/*`，hub 密钥）。派活台是另一条路，两条互不借用：

| | 多设备推送（已有） | 派活（新） |
| --- | --- | --- |
| 方向 | 各电脑 → 中心机，只读摘要 | MacBook → Mac Studio，控制 |
| 端口 | Studio 8443 → 127.0.0.1:7788 | Studio 8444 → 127.0.0.1:7790（只挂派活路由） |
| 凭据 | hub 密钥（所有设备共用） | 每台设备一把派活密钥 |
| 内容 | 不含对话、命令、路径 | 任务文字、审批命令按需实时取，不落 MacBook 的库，也不进 hub 摘要 |

- 普通远程访问仍按 `remoteBlocked` 只读，`/api/managed*` 与对话接口对普通远端照旧拒绝。派活路由只在 7790 上存在，7788 上没有。
- hub 摘要里派活台发起的工作项和普通工作项一样，只带编号、标题、状态。MacBook 在小镇“Mac Studio”片区里看到它们，点进去打开派活台。
- 派活密钥不能换出面板 cookie、hub 密钥或 `remote.token`，反过来也一样。

## 4. 界面

两台电脑打开的是同一个页面 `/?view=dispatch`，页头写明“任务在 Mac Studio 上执行”和 Studio 在线状态、Codex 版本。

- **左栏：任务列表。** 每件标出状态：执行中、等你决定（有审批）、菜熟了·等验收（Agent 已交付）、已交给电脑（控制已释放）、停了（本轮停止或出错）。底部“交代新任务”：选一个 Studio 上授权过的项目，写任务。
- **右栏：选中的任务。**
  - 最上面是待批准的命令：`仅允许这一次` / `拒绝`。命令正文实时从 Studio 取来显示，不保存。
  - 中间是“交代下一步”（`在 Mac Studio 执行` / `停止本轮`）和最近发生的事（只列类型和时间，例如“改了 3 个文件”“跑了测试”）。
  - 底部是 `去小镇看这栋房子` 和 `回电脑接着做`。
- **谁在控制。** 页头显示当前控制者，例如“MacBook 正在控制 · 1 分钟前”。另一台要用就点“接过来”，旧的一方马上变成只看。
- **Studio 专有：** “已配对设备”（配对、收回）和“可派活的项目”（添加、移除）。这两块在 MacBook 上不显示，也没有对应的远程接口。
- **小镇入口：** 广场上加派活台桌子；Studio 片区里派活台发起的房子门口挂一个小牌子，点进去直接到该任务。

MacBook 上页面只和 MacBook 本机的 `steward serve` 通信，由本机服务带着派活密钥去找 Studio。密钥不进浏览器。

## 5. 配对、密钥与每次请求的检查

**配对**

1. 在 Studio 的派活台点“配对新设备”，得到一个 8 位一次性配对码，10 分钟内有效，只显示在 Studio 屏幕上。
2. 在 MacBook 的派活台输入配对码和设备名。MacBook 服务通过 8444 换回该设备的派活密钥，存到 `~/.steward/dispatch.key`（0600），不写进 `config.json`，不打印。
3. Studio 只存密钥的哈希、设备名、权限、配对时 Tailscale 报告的登录身份、配对时间和最近使用时间。

**权限**按动作分开记：`start`、`input`、`interrupt`、`resume`、`deny`、`allow`、`handoff`。按 U06，MacBook 默认全部打开；以后手机可以单独少给。

**收回**：Studio 上点“收回”立即失效，正在进行的控制租约一起作废，执行中的本轮不会被停掉（停不停由用户另点）。MacBook 上点“忘记这台 Studio”只删除本机密钥，Studio 那边仍要收回才算完。

**每次请求的检查**（缺一项就拒绝，并写审计）：

- 请求经 Tailscale serve 到达 7790，带有 Tailscale 身份头，且与配对时的登录身份一致；带 Funnel 标记的请求一律拒绝。
- `Authorization` 中的派活密钥哈希匹配、未收回，并且有这个动作的权限。
- 写操作必须持有当前控制租约和 epoch；审批还要核对请求指纹，且该审批仍在等待。
- Host 只认 Studio 的 `.ts.net` 名称和 8444。

## 6. 执行与回到桌面 App

- **用真实 Codex 环境。** 原型用隔离的 CODEX_HOME，桌面 App 看不到那条会话。派活台要让桌面 App 能接手，必须用 Studio 上用户自己的 Codex 环境启动 `codex app-server`。和原型一样，只用命令行参数关掉子进程的 hooks、插件，不改用户的 Codex 配置；避免和 SS 自己的 hook 重复回报。
- **每件任务一个工作树。** 沿用托管会话（LaunchManaged）的做法：在授权项目里为每件任务新建分支和工作树，任务之间互不干扰。MacBook 只能选项目、写任务文字，不能指定目录、命令、模型或执行电脑。
- **页面断开继续跑。** 执行进程属于 Studio 的服务。MacBook 合盖、断网、关页面都不影响；回来时复用小镇“你离开期间”的提示。
- **回到桌面 App 的流程：**
  1. 在任意一台点“回电脑接着做”：等本轮结束（或先停止），释放控制，任务标为“已交给电脑”。
  2. Studio 的派活台顶部出现“这件等你在桌面 App 接着做”，点按钮打开 `codex://threads/<会话号>`。MacBook 不能远程在 Studio 屏幕上打开 App。
  3. 之后用户在桌面 App 里继续，SS 已有的 Codex hook 照常回报，按同一会话号归到同一个工作项。
- **前提：K2 点验。** 先在 Studio 上证明：由 app-server 发起的会话，桌面 App 能用 `codex://threads/<会话号>` 打开，看得到之前的历史，并能在同一会话里继续。不通过就停下报告（U06：不接受只给命令行）。

## 7. 审批

- 两台都可以“仅允许这一次”或“拒绝”。允许只对这一条请求生效，不生成“以后都允许”的规则。
- 两台同时决定时，先到的生效，后到的返回 409，并显示“已在 MacBook 上允许”这类结果。
- 命令正文只在显示时从 Studio 实时取，不写 MacBook 的数据库、不写审计、不进 hub 摘要、不进通知文字。
- 文件修改等原型还没有完整允许链路的请求，保持“只能拒绝”，直到另做验证。

## 8. 数据与审计

- 控制状态统一进现有的 `managed_sessions` / `managed_audit`，按 D0 不另建第二套状态机。`managed_sessions` 现在假定 tmux（`tmux_name` 唯一且必填），需要一次迁移加上运行方式（tmux 或 Codex app-server）和原生会话号；迁移编号按任务索引的唯一登记处分配。原型的映射文件逐项迁到这里，迁不过来的写清楚原因，不两份并存。
- 新增“已配对设备”表：设备名、密钥哈希、权限、Tailscale 登录身份、配对时间、最近使用时间、收回时间。
- `managed_audit` 增加“哪台设备”。每个动作记设备、动作、时间、结果；任务文字和命令只记长度，不记内容。

## 9. 手机：微信入口（U09，未定，本批不做）

用户希望像 Hermes 一样在微信里管理。要先定下面几件事，再写任务书：

1. **内容会经过腾讯和 gateway。** 现在的规则是审批内容、命令和对话不出用户自己的设备。走微信等于把它们发给第三方。需要决定微信里能出现什么：只出现“第 3 件等你批准 · 执行命令”，回复“允许 3 / 拒绝 3”；还是连命令正文也发。
2. **gateway 在哪台机器上、怎么认人。** 要先看 Hermes 的微信 gateway 是怎么运行、怎么确认消息来自你本人的（K4 只做这项调研，不接入）。
3. **允许靠一句微信回复够不够。** 微信账号被别人拿到就能批准命令。可选做法：微信里只能拒绝和查看，允许要点开一个只在 tailnet 内能开的链接。

这是新的控制入口和新的外发渠道。按仓库规则，先改设计文档并得到用户确认，再动手。

## 10. 不做

- 不改现在的 8443、hub 推送、`remoteBlocked`、其他工具的 hooks、Tailscale 配置或用户的 Codex 配置；8444 由用户自己执行 `tailscale serve`。
- 不开 Funnel 或任何公网入口。
- 不让 MacBook 执行任务，不让 Studio 控制 MacBook。
- 不做 Ekko 的模型/供应商管理、工作区管理、会话库；不引入 Vue、Koa 或新依赖。
- 不在本批做微信入口，也不做 Claude/Hermes 的派活适配（原型说明里的后续接入点不变）。
- 不替用户合并、发版、替换任何一台的正式安装。
