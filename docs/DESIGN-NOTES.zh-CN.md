# Session Steward 设计笔记

## 多个 Agent 同时工作，人该先看哪里？

同时开着 Claude Code 和 Codex 时，我得在几个窗口之间来回找，确认哪项工作还在推进、哪份交付等我查看、哪条命令需要我批准。SS 小镇把项目画成房子、会话画成门口的小人。待处理的交付是菜地里熟了的菜，等待决定的请求挂在告示栏上。走进项目房间，还能沿着项目概况、功能地图、当前推进、验证依据往下读。地图负责指路，点开后才能看到做判断需要的记录。见 [README](../README.md#为什么做它) 和[项目结构资料](project-structure.md)。

## 一、工作项、会话、运行、审批各有自己的状态

工作项回答「这件事做到哪了」，会话回答「这个 Agent 窗口现在在做什么」，运行记录「这一轮执行发生了什么」，审批记录「这个具体请求处理到哪一步」。同一个会话转去做另一项工作时，原来的运行以「转交」结束，再为新工作开一轮。`Stop` 表示一轮回复结束，会话转为空闲，工作项仍按原状态显示。迟到的事件按发生时间归到当时的工作项和运行。一次权限决定绑定请求 ID 和内容指纹，执行确认等后续的工具事件。见[开发约定](../AGENTS.md)和[使用手册的关键语义](GUIDE.zh-CN.md#关键语义)。

## 二、交付与用户验收分别记录

Agent 提交 `deliver` 后，普通工作项进入待验收，用户可以看交付说明，决定标为「已处理」或退回。功能进度会标出 Agent 回报的验证结果及对应候选，也单独记录用户是否确认该候选符合要求。用户验收绑定功能、候选和范围。候选一变，旧验收就不能沿用。采集凭据也没有权限代用户确认验收。这让后来接手的人看得出证据来自哪一版、结论是谁给的。见[核心功能进度的验收规则](CORE-FEATURES.md#一致性和验收)和[工作项的处理方式](GUIDE.zh-CN.md#工作项的已处理)。

## 三、安装器只管理自己的 hooks

Claude 和 Codex 的配置也可能被其他工具使用。首次安装会备份原配置，新增的 Steward 条目带有自己的标识，重复安装只替换这些条目。安装后若有人改过配置，卸载会按标识移除 Steward 的条目，保留其他改动。Codex 用户还要在客户端里自己信任新 hooks。见[开发约定](../AGENTS.md)和[安装与卸载说明](GUIDE.zh-CN.md#快速开始)。

## 四、事件留在本机，默认保存脱敏信息

服务监听本机回环地址，运行数据默认保存在 `~/.steward`。采集凭据与面板凭据分开，面板写操作还要检查请求来源。默认保存的事件信息包括事件类型、工具名、指纹，以及截断并遮蔽密钥后的预览。原始事件和完整对话不入库。可选的远程只读查看和多设备摘要有各自的边界。见[安全策略](../SECURITY.md)和[使用手册的安全与隐私](GUIDE.zh-CN.md#安全与隐私)。

## 做完才想明白的事

回头看，我把第一轮做得太宽了。除了看进度、收交付和处理权限，还做了托管会话、交接和复盘。手册里记录了好几项可选功能只用合成数据测试，真实使用经验仍少。我也太晚把东西交到别人手上。如果重做，我会在「看到一项工作、找到一份交付、作出一次决定」能跑通时就给人用，先看他们能不能走完，再决定哪些功能值得做。见[手册中的支持情况](GUIDE.zh-CN.md#支持情况)和[公开试用说明](TRYOUT.zh-CN.md)。
